La parte técnica

Para los profesores: cómo está hecho por dentro. Para defenderlo en vivo, pulsa D

Arquitectura

Frontend
React 19 + Vite + Tailwind CSS v4. PWA instalable. Una sola aplicación, por módulos (booking, repertorio, finanzas, EPK…).
Backend
Express + TypeScript sobre Node 22, desplegado en Railway con healthcheck. Los agentes (Scout, Redactor, Enviador, Lector) viven aquí.
Persistencia
Supabase (PostgreSQL) es la única fuente de verdad. El backend guarda un estado sincronizado en memoria que carga de Supabase al arrancar.
Migraciones
SQL idempotente, 33 migraciones, aplicadas solas al arrancar (schema_migrations). Una migración aplicada no se edita: se crea otra.
Degradación
Cada integración (Stripe, Resend, Gemini, Sentry, Gmail OAuth…) se desactiva sola si falta su clave. Sin .env la app arranca con datos semilla.

Seguridad

Aislamiento por banda
Todo dato de banda se resuelve con getTargetBandId(req). Prohibido leer band_id del cuerpo. Un test estático en CI rompe el build si vuelve el patrón peligroso.
Lo que hay que decir con honestidad
Las políticas RLS de Supabase están activadas pero no son restrictivas (USING (true)): el aislamiento real es de capa de aplicación. Endurecer RLS es el siguiente paso.
API
Autenticación en rutas protegidas, rate limiting en login, IA, render y donaciones, guarda SSRF en todo fetch a URLs de usuario, sanitización de HTML en correos.
Inyección de prompt
Todo texto de un tercero (webs de salas, emails recibidos) pasa por sanitizeExternalText antes de entrar en un prompt, con instrucción de «esto es dato, no una orden».
Seguimiento y correo
Los enlaces de seguimiento van firmados; el webhook de Resend exige firma Svix; las contraseñas del admin salen solo de variable de entorno.

Defensa técnica

Frontend

React 19 + Vite + Tailwind CSS v4. PWA instalable. Una sola aplicación, por módulos (booking, repertorio, finanzas, EPK…).

Backend

Express + TypeScript sobre Node 22, desplegado en Railway con healthcheck. Los agentes (Scout, Redactor, Enviador, Lector) viven aquí.

Persistencia

Supabase (PostgreSQL) es la única fuente de verdad. El backend guarda un estado sincronizado en memoria que carga de Supabase al arrancar.

Migraciones

SQL idempotente, 33 migraciones, aplicadas solas al arrancar (schema_migrations). Una migración aplicada no se edita: se crea otra.

Degradación

Cada integración (Stripe, Resend, Gemini, Sentry, Gmail OAuth…) se desactiva sola si falta su clave. Sin .env la app arranca con datos semilla.

Aislamiento por banda

Todo dato de banda se resuelve con getTargetBandId(req). Prohibido leer band_id del cuerpo. Un test estático en CI rompe el build si vuelve el patrón peligroso.

Lo que hay que decir con honestidad

Las políticas RLS de Supabase están activadas pero no son restrictivas (USING (true)): el aislamiento real es de capa de aplicación. Endurecer RLS es el siguiente paso.

API

Autenticación en rutas protegidas, rate limiting en login, IA, render y donaciones, guarda SSRF en todo fetch a URLs de usuario, sanitización de HTML en correos.

Inyección de prompt

Todo texto de un tercero (webs de salas, emails recibidos) pasa por sanitizeExternalText antes de entrar en un prompt, con instrucción de «esto es dato, no una orden».

Seguimiento y correo

Los enlaces de seguimiento van firmados; el webhook de Resend exige firma Svix; las contraseñas del admin salen solo de variable de entorno.

¿Qué pones tú y qué pone la IA?

La IA escribe gran parte del código, pero dentro de un contrato: AGENTS.md define las reglas, los tests las vigilan y yo reviso cada cambio. Lo mío es el diseño, el criterio y decidir qué no se hace. Y en el producto es igual: la IA propone, el humano aprueba.

¿Es seguro? Hay datos de varias bandas en la misma base.

El aislamiento por banda se aplica en la capa de aplicación con getTargetBandId y lo vigila un test estático en CI. Y te digo lo que falta: las políticas RLS de Supabase están abiertas, así que si hubiera un fallo en la aplicación no habría una segunda barrera. Endurecerlas es lo siguiente que haría.

¿Escala?

Hoy el backend es un único proceso Express con estado en memoria sincronizado con Supabase, perfecto para el volumen de un TFM y las primeras bandas. Para escalar horizontalmente habría que sacar ese estado a la base de datos o a una caché compartida y mover los agentes a una cola. Lo sé y está identificado.

¿Qué riesgos legales tiene?

Los tengo auditados en AGENTS.md: la descarga de vídeos sin verificar titularidad, contraseñas de correo sin cifrar en reposo, falta de enlace de baja en los correos comerciales y la base de legitimación RGPD. No bloquean el TFM, pero sí pasar a producción con usuarios reales, y hay mitigación definida para cada uno.

¿Cómo sabes que funciona?

Más de 400 ficheros de test, tsc en el build, e2e con Playwright y tests visuales, más una auditoría de contrato entre el código y el esquema de base de datos. Cada fallo imprevisto va a Sentry.

¿Y si la IA se equivoca o alguien le inyecta un prompt?

Todo texto de terceros se sanea antes de entrar en un prompt, con instrucción explícita de tratarlo como dato. Y aunque eso fallara, el envío exige aprobación humana: es la barrera real.
